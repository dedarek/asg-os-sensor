## 1. 项目目标与使用场景

ASG 是一个面向本机 AI Agent 的发现、资产调查与运行治理原型。它从操作系统进程和关联信息开始，识别候选 Agent 及相关组件，调查模型、MCP、工具、技能、规则和网络端点，然后尝试建立可观测、可验证的 Hook 接入。

产品期望的使用体验是：用户部署服务、正常打开 Agent，在页面上扫描后，系统自行识别可复用通道；能直接接入的先接入，不足之处再由 Goose 调查。页面展示查到了什么、实际收到什么事件、控制是否真正生效。

主要场景：

- **资产摸底**：本机有哪些候选 Agent、模型网关、工具服务和宿主；它们使用哪些模型、工具、技能和规则。
- **接入验证**：目标是否具备可用 Hook 或插件扩展点，是否安装、加载、产生真实事件。
- **活动审计**：查看用户输入、助手输出、模型调用与工具操作及其关联关系。
- **执行控制验证**：在支持同步拦截的位置，将操作交给策略服务决定放行、拒绝或等待人工确认。
- **接入经验复用**：保留协议实现、结构指纹和已学习配方，减少相同兼容环境下的重复调查。

当前主要验证环境为 macOS。本仓库有跨平台代码和启动脚本，但不能由此推导出 Windows、Linux 上的完整发现与接入已通过同等验收。

## 2. 当前能力与范围

| 能力 | 当前实现 | 使用边界 |
|---|---|---|
| 手动与周期扫描 | 已实现；周期可在页面修改并保存 | 轮询可能漏掉短命进程；系统权限影响可见范围 |
| 候选发现与进程归属 | 进程结构、行为信号、入口元数据、可选身份提示 | 分数是识别线索，不是危险程度或准确概率 |
| 身份与角色判断 | 程序提供证据，Goose 调查角色 | 候选、确认 Agent、网关、工具服务等需分别展示 |
| 资产调查 | 模型、MCP、工具、技能、规则、网络等分类结果 | 配置存在、安装存在、当前激活和真实调用分别记录 |
| 协议快速接入 | 兼容命令式 Hook 可直接安装，无需先调用 Goose | 仅覆盖已识别配置结构；ACP 需由受管 stdio 启动，不能接管任意既有会话 |
| Goose 补充适配 | 读取目标相关证据，生成文件安装方案 | 对未知机制仍需调查，不保证任意软件都可注入 |
| 安装与回滚 | 作用域检查、哈希前置条件、事务备份、写入与回滚 | 文件存在不等于目标已加载；原生信任机制仍可能阻止加载 |
| 统一事件与正文展示 | 原始记录、归一化记录、会话正文、自检结果 | 没有采集到的正文不能从工具记录或模型摘要推测 |
| 工具执行控制 | 同步决策接口和目标侧客户端 | 只有目标等待且遵守决定，才能实际阻断 |
| 实例级自动自检 | 8 项检查；实际证据驱动状态 | 无流量为待验证；不会自行在用户会话制造测试副作用 |
| 独立 Hook 服务 | 已实现；服务已绑定事件和控制，不做扫描或调查 | 要保留运行依赖、绑定、凭据和目标侧 Hook，不能删掉全部组件 |
| 配方包导出导入 | 已实现本地工程能力 | 不等于跨机器兼容与安装全部验收通过 |
| AI Trust 对接 | 有连接器、字段映射和重试队列实现 | 当前接口契约需与真实平台确认，尚不能宣称平台接管通过 |

本文编写时，本机 `8081/api/state` 和 `8099/health` 均可访问；这是服务可用性检查，不是所有 Agent 接入完成的证明。

## 3. 总体架构与模块职责

系统分为发现调查、目标接入、事件观测、执行控制和展示服务几个部分。

```text
操作系统进程 / 入口 / 配置 / 关联目录
                  │
                  ▼
          发现与实例身份绑定
                  │
                  ▼
       可复用协议或兼容历史配方
          │                 │
     可直接尝试          未识别或存在缺口
          │                 ▼
          │           Goose 证据调查
          │                 │
          └───────┬─────────┘
                  ▼
          校验、授权范围、安装
                  │
          目标加载并执行 Hook
             ┌────┴────┐
             ▼         ▼
          事件日志    执行前决策
             │         │
             ▼         ▼
        实例绑定与归一化  放行 / 拒绝 / 确认
             │         │
             └────┬────┘
                  ▼
       页面 / API / 自动自检 / 独立验收
```

| 组件 | 主要职责 | 主要代码 |
|---|---|---|
| 发现与画像 | 进程候选、结构信号、入口身份与归属 | `asg_os_sensor.py`、`runtime/analyzer.py`、`runtime/identity.py` |
| 页面与调度 | 扫描、排队、调查生命周期、API、前端 | `monitor_dashboard.py`、`web/dashboard.html` |
| 协议快速路径 | 在 Goose 前尝试复用命令式 Hook | `runtime/protocol_fastpath.py`、`runtime/command_protocol_hook.py` |
| 协议证据检查 | 检查结构、约束配方选路 | `runtime/integration_protocol.py` |
| Goose 工具 | 读取目标上下文、配置、入口、证据、调查结果 | `runtime/analyst_tools.py`、`runtime/analyst_evidence.py` |
| 调查指令 | 资产调查、机制学习、一般调查 | `recipes/runtime_assets.yaml`、`runtime_hook_analyst.yaml`、`runtime_analyst.yaml` |
| 接入执行 | 计划、作用域、文件事务、绑定与复用 | `runtime/onboarding.py`、`runtime/learned_onboarding.py`、`runtime/learned_install.py` |
| 指纹与兼容 | 结构匹配、版本信息、配方存储 | `runtime/matcher.py`、`runtime/compatibility.py`、`runtime/recipe_bundle.py` |
| 观测 | 日志来源绑定、实例过滤、事件快照 | `runtime/observation_registry.py`、`runtime/observation_source.py`、`runtime/hook_data.py` |
| 统一格式 | 原生事件名称与内容归一化 | `runtime/event_vocabulary.py`、`runtime/protocol_events.py` |
| 验收 | 输入输出配对、逐项自检、实际控制证据 | `runtime/io_acceptance.py`、`runtime/integration_selfcheck.py`、`runtime/hook_acceptance.py` |
| 控制 | 策略、等待确认、返回决定与回执 | `runtime/hook_control.py`、`runtime/hook_control_client.py` |

Goose 负责解释证据与提出适配方案；程序负责安装动作、实例绑定和验收状态。Goose 写出“支持”或“成功”的文字，不会直接替代程序侧的事件与效果检查。

## 4. 从发现到治理的完整流程

### 4.1 扫描与冻结实例

扫描获取 PID、创建时间、进程树、可执行入口和可访问的相关信息。每个目标使用 `pid:create_time` 作为本机实例标识。例如 `12345:1780000000.123`。

创建时间用于区分 PID 复用。重启后，即使程序名称和路径相同，也属于新实例。旧实例的事件、加载成功和控制通过状态不能直接转移。

### 4.2 候选识别与角色确认

画像信号用于决定哪些进程值得进一步调查。入口名称、模型 SDK、配置目录、子进程和协议结构都可能提供线索，但单独一项通常不足以证明“确认 Agent”。

页面将 Agent 与待确认候选、其他类别分开展示。其他类别可包含模型网关、工具服务、宿主程序等。普通应用被列为候选后，经调查可修正为其他类别；这是分类结果，不是其已被 Hook 接管。

### 4.3 协议或配方接入

对需要自动调查的目标，在启动 Goose 前尝试协议快速路径。已登记观测绑定会被保留；历史兼容配方继续走原有复用流程。不能直接接入时，Goose 取得目标证据并补充调查。

### 4.4 安装与等待激活

安装器校验目标仍存活、目录授权、文件计划和哈希前置条件，保存备份并写入配置或插件。目标可能需要新会话、重启或通过自身的信任准入才能加载。

安装后页面应显示“已安装，等待加载”，直到当前目标执行真实回调。不能因为配置文件写入成功就改为完整观测或控制通过。

### 4.5 持续观测与反馈

Hook 写入日志，服务按绑定过滤当前实例事件。归一化层提取会话、调用编号和正文，自动检查缺口。协议快速路径未激活或能力不足时，将安装信息和缺失项交给 Goose，避免重新从零调查整个产品。

## 5. 协议优先与 Goose 回退

### 5.1 当前命令式 Hook 快速路径

当前实现基于配置结构识别命令式 Hook，而不是产品白名单：

1. 从目标进程相关的受限 JSON 配置中提取协议结构。
2. 找到唯一可直接处理的顶层 `hooks` 配置。
3. 确认对应目录位于部署授权范围。
4. 识别直接 command 条目或包含 matcher 的 command 分组。
5. 在已存在、可处理的事件列表中追加通用回调，保留原回调。
6. 写入 `.asg-command-protocol/hook.py`、`client.json`，建立实例观测绑定。
7. 从目标真实回调检查加载和正文等能力。

支持处理的原生事件名称为 `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PostToolUse`、`Stop`。实际追加哪些事件取决于配置中已经存在的兼容条目；不会仅凭产品名字补齐所有事件。

模板执行时，从自身祖先进程中查找已登记的 PID 与创建时间。共享配置中的另一个未登记实例不会被直接归为当前目标。

### 5.2 回退条件

| 情况 | 系统处理 |
|---|---|
| 未找到唯一可安装配置 | 回退 Goose，继续调查路径与机制 |
| 配置布局不支持或安装前置条件变化 | 保留错误与已有文件，回退调查 |
| 已有绑定 | 保留绑定，继续原来的验证和复用流程 |
| 安装后没有活动且未满 120 秒 | 等待激活，不能算失败或通过 |
| 安装后超过等待窗口仍无活动 | 把激活问题交给 Goose；不自动重启目标 |
| 有真实回调但仍缺模型、回合或控制证据 | 把缺失检查项写入升级请求，由 Goose 补充 |

120 秒是当前快速路径的等待策略，不是所有 Agent 的启动承诺，也不意味着超时后强行注入。

### 5.3 Goose 的输入与输出

Goose 可以读取目标上下文、入口、配置表面、相关文件和已有证据，提交结构化资产发现。生成新接入配方前，必须调用 `inspect_integration_protocols`，并在 `integration` 中引用当前目标的检查证据。

配方主要字段：

| 字段 | 内容 |
|---|---|
| `agent_identity_name`、`confidence` | 身份判断与置信表达 |
| `match_features` | 结构与兼容匹配线索 |
| `integration` | 协议家族、证据、缺失能力、回退理由 |
| `investigation` | 身份与资产调查结果 |
| `hook` | 方法、工作目录、是否需重启、能力、验证和回滚描述 |
| `install_plan` | 文件路径、内容和修改前 SHA-256 |
| `observation_source` | 日志路径与字段映射；目标实例由执行器绑定 |
| `evidence_refs` | 支撑方案的真实观察证据编号 |

`integration.family` 支持 `command_hooks`、`acp`、`plugin`、`unsupported`。选择插件或跳过已有通道时，要解释已有通道为什么不能满足缺失能力。

### 5.4 ACP、MCP 与 OpenTelemetry 的位置

- **ACP**：已有结构识别和消息归一化。提供通用 ACP v1 stdio 桥接和 agent_servers 配置包装，实际握手后登记子实例。只有实际接入传输后才能收到消息，检测到协议字样不会产生数据。
- **MCP**：帮助理解和访问工具通道，覆盖的是经过该通道的调用，不能默认代表整个 Agent 的对话、内部模型请求和所有操作。
- **OpenTelemetry**：本项目对齐部分语义字段，例如会话和工具调用编号。现已提供 OTLP/HTTP JSON/protobuf logs/traces 接收及 GenAI 内容映射；这不等于完整 OTLP 导出，更不等于遥测通道天然能够阻断执行。

ACP 的助手消息片段不会被自动当作完整模型响应；可选的权限请求也不会被自动当作所有工具都受控的证明。

## 6. 资产与角色模型

资产调查优先回答“是什么、在哪里、依据是什么、是否实际激活”。

| 类别 | 期望展示的基本信息 | 常见误判 |
|---|---|---|
| 模型与网关 | 提供方、模型标识、入口地址、配置来源 | 配置里有模型不代表本轮已调用 |
| 工具 / MCP | 名称、传输方式、命令或端点、声明位置、运行证据 | 插件清单声明不代表服务已经运行 |
| Skills | 名称、基本介绍、文件路径、所属目录、发现范围 | 找到目录不代表列全；已安装不代表本轮已使用 |
| 规则 | 文件名、位置、摘要、来源范围 | 同目录规则不一定被目标加载 |
| 网络端点 | 可观察端点、关联进程、来源 | 监听端口不等于模型网关身份 |
| 执行事件 | 工具名称、调用编号、参数、结果、时间 | 子进程快照不等于完整历史执行日志 |

结果状态应区分：已采集、范围内未发现、未采集、待确认、失败、不支持。展示“未发现”时，应保留检查范围；不能把一次有限查询的空结果写成“没有技能”或“没有 MCP”。

非 Agent 卡片使用较少字段：类别、用途、版本、服务或端点、关联组件、判断依据和调查范围，不强行显示 Agent 的 Hook 接入字段。

## 7. Hook、事件与输入输出

### 7.1 Hook 的定义

本项目中的 Hook 是插入目标生命周期或执行路径的回调。挂接位置决定能看见什么：

- 用户提交入口可采集用户输入。
- 助手完成入口可采集助手输出。
- 模型传输入口可采集模型请求、响应及重试。
- 工具执行入口与结束回调可采集参数和结果。
- 同步执行前入口可以接入控制决定。

某个回调加载成功，只能证明该回调路径生效；不能自动推导其他入口也已接通。

### 7.2 统一事件名称

| 事件 | 语义 |
|---|---|
| `hook.loaded` | 当前实例执行了加载或回调生效路径 |
| `user.input` | 用户输入 |
| `assistant.output` | 助手输出；可能是片段，需看完整标记 |
| `model.request` / `model.response` | 模型请求与响应 |
| `tool.execute.before` / `tool.execute.after` | 工具执行前与执行后 |
| `tool.error` | 工具失败 |
| `io.turn.end` | 本轮生产端计数与序列检查点 |
| `session.start` / `session.end` | 会话生命周期 |
| `permission.request` | 请求决定；本身不是执行效果 |

无法识别的原生事件保留原始记录，并在词表信息里显示，避免悄悄丢弃。

### 7.3 记录的三种视图

1. `records`：通过实例过滤的原始记录，带时间、行号和目标信息。
2. `normalized_records`：增加统一事件、标识、正文与映射说明。
3. `conversation`：提取便于人阅读的用户和助手正文。

原始日志与归一化结果分别保留，便于定位“没采到”与“采到了但前端没提取出来”之间的差异。

### 7.4 标识与完整性字段

| 字段 | 用途 |
|---|---|
| `instance_id` | 本机具体进程实例 |
| `session_id` | 会话；可映射 `gen_ai.conversation.id` |
| `turn_id` | 回合 |
| `agent_id` | Agent / 子 Agent 区分 |
| `request_id` | 模型调用；每次重试应有不同编号 |
| `tool_call_id` | 工具调用；可映射 `gen_ai.tool.call.id` |
| `event_id` | 事件唯一编号 |
| `sequence` | 回合内序号 |
| `content` | 实际正文、参数或结果 |
| `content_complete` | 生产端是否声明内容完整 |
| `truncated` | 是否截断 |

示例为统一记录的说明形式，不是现有实例的真实消息：

```json
{
  "instance_id": "12345:1780000000.123",
  "event_type": "user.input",
  "payload": {
    "event": "user.input",
    "session_id": "session-demo",
    "turn_id": "turn-1",
    "event_id": "event-1",
    "sequence": 1,
    "content": "请解释当前项目的目录结构",
    "content_complete": true,
    "attributes": {"gen_ai.conversation.id": "session-demo"}
  }
}
```

生产端缺少会话、回合或调用编号时，归一化层不会补造。这类记录可展示，但不能据此通过完整关联验收。

### 7.5 流式、重试和有界窗口

完整流式响应必须等流结束后才能声明完整。断流、截断或仍在生成的片段应保留未完成状态。重试需要新的请求编号，避免多次请求被合并成一次。

HTTP 读取使用有限条数和字节窗口。页面看到的可能只是日志尾部；窗口截断、未完成行和解析错误都会影响完整性判断。大批次验收应读取保存的生产端日志，并对照独立入口记录，而不是只对 HTTP 返回的最近若干条计数。

## 8. 控制决策与实际执行

### 8.1 控制链路

```text
目标即将执行工具
    → Hook 提交具体操作
    → 决策服务匹配策略
    → allow / deny / ask
    → Hook 等待最终决定
    → 目标执行或停止执行
    → 回执与独立副作用核对
```

策略支持默认决定，以及按工具名称和可选 PID 匹配的规则。`ask` 会等待确认；超时会返回拒绝。当前通用命令式 Hook 在控制客户端报错或超时时拒绝该操作。

决定是放行还是拒绝，与目标是否执行决定，是不同事实。`decision.returned` 证明服务返回了决定；`ack` 证明生产端声明收到并应用了决定；它们都不能单独证明被拒绝的文件没有创建、命令没有执行或网络请求没有发出。

### 8.2 控制验收

控制通过需要同一实例、同一 Hook 文件版本下的三类独立证据：

- `allow_effect`：放行后，期望副作用发生且内容正确。
- `deny_effect`：拒绝后，期望被阻止的副作用没有发生。
- `decision_wait`：故意延迟决定时，在决定返回前没有提前执行。

例如在隔离目录让 Agent 创建带唯一随机标记的文件：拒绝批次文件不存在；放行批次文件内容一致；等待批次在未决定期间始终不存在。不能仅检查 Agent 回复“已拒绝”。

### 8.3 访问范围

控制接口对远程调用默认关闭。显式设置 `ASG_HOOK_REMOTE=1` 后，远程请求仍需 Bearer 凭据。`decision` 与 `ack` 即使从本机调用，也要求 Hook 凭据。

看板的其他管理接口并未全部套用同样的鉴权。因此，开启局域网展示不等于获得完整的多用户权限系统。当前看板适用于受控开发与演示网络；需要生产发布时，应先补统一认证、接口授权和传输保护。

## 9. 实例身份、配方与复用

复用分为两个层面：

| 层面 | 复用对象 | 仍需检查 |
|---|---|---|
| 协议复用 | 通用命令式 Hook 实现 | 目标配置兼容、实际加载、能收到的内容和控制语义 |
| 指纹配方复用 | 历史调查与学习所得方案 | 当前结构与构建兼容、原证据、文件条件、授权和新实例绑定 |

匹配不是按显示名称相同就通过。兼容检查会考虑可执行内容、入口、运行时、平台及启动相关信息，但配置、依赖、MCP、插件集合和模型路由不一定完全处于同一兼容快照的覆盖范围。

旧实例的通过状态在以下变化后需要重新核实：目标重启、PID 复用、Hook 字节变化、绑定变化、事件字段变化、关键配置变化。

配方包导入用于交换方案与证据材料，不会把来源机器的“已加载”和“控制通过”直接变成目标机器的事实。跨机器还需要路径、解释器、权限、依赖和实际目标验收。

## 10. 安装、部署与配置

### 10.1 环境准备

建议使用 Python 3.10 或更高版本。核心 Python 依赖为 `psutil`、`pyyaml`、`requests`、`python-dotenv`。Goose 调查需要本机 Goose CLI 和可用模型服务。Node.js 等目标侧依赖由目标或具体 Hook 方案决定，不是每条 Python 协议路径都必需。

在仓库根目录执行：

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

已经有 `.env` 时直接编辑现有文件，不要用示例覆盖凭据。配置文件不得提交真实 API Key。

### 10.2 只看扫描与页面

下列配置适用于先确认服务可启动、依赖可用的场景：

```bash
export ASG_HOST=127.0.0.1
export ASG_PORT=8081
export ASG_RUN_DIR="$PWD/artifacts/local-demo"
export ASG_AUTONOMOUS_ANALYSIS=0
export ASG_ONBOARDING_AUTO_INSTALL=0
python monitor_dashboard.py
```

打开 `http://127.0.0.1:8081/`。此模式不应当作为“自动协议接入已开启”的演示：当前自动接入尝试位于自动调查调度入口，关闭自动调查也会影响这条调度路径。

### 10.3 启用自动接入与 Goose

在 `.env` 中配置模型路由或使用页面模型设置，再配置以下环境变量。授权目录必须替换为准备允许 ASG 修改的实际目标配置目录。

```bash
export ASG_HOST=127.0.0.1
export ASG_PORT=8081
export ASG_RUN_DIR="$PWD/artifacts/local-demo"
export ASG_PIPELINE=1
export ASG_AUTONOMOUS_ANALYSIS=1
export ASG_ONBOARDING_AUTO_INSTALL=1

export ASG_ONBOARDING_SCOPE=project
export ASG_ONBOARDING_WORKSPACE_ROOTS="/absolute/path/to/authorized-config"
```

以上为开发者前台调试入口，请先在虚拟环境中安装依赖。日常部署使用 `setup.sh` / `setup.bat`，之后使用 `python deploy.py start|stop|status|doctor`；`start_dashboard.*` 仅兼容转发到 `deploy.py start`，读取 `deployment.local.json`。不要在同一个端口重复启动服务。

Goose 不可用时，已匹配的协议快速尝试仍可先执行；需要回退 Goose 的目标会明确报告不可用。协议接入无需 LLM 调用，不等于整个自动发现调度目前已完全独立于调查开关。

需确认设备网络可达与系统防火墙允许。页面可访问与远程控制接口可调用是两套检查，后者还涉及远程开关和凭据。

### 10.6 模型设置与验证

页面配置 API 基础地址、模型名称和 API Key。保存流程使用真实 Goose 调用进行验证，收到预期助手回复后才落盘；失败保留原配置。更换服务地址时不能自动沿用旧地址凭据。读取配置接口只返回是否已有 Key，不返回 Key 原文。

命令行 `python verify_llm.py` 可检查模型路由，但页面“Goose 可实际返回消息”的验证与单纯 HTTP 联通是不同层次。

## 11. 页面使用说明

### 11.1 新 Agent 的使用步骤

1. 正常安装并启动目标 Agent，进入可交互界面。
2. 打开看板，点击扫描，或等待扫描周期。
3. 在候选或确认 Agent 中找到目标，核对 PID 与实例身份。
4. 查看调查、分类、观测与接入小卡片。
5. 安装后若提示等待加载，按目标要求新开会话或重启目标。
6. 在目标里进行一轮正常聊天；需要验证工具时，再发起可控的工具任务。
7. 点击“Hook 实时数据”，查看正文、原始记录和逐项自检。
8. 若缺少内容，查看缺失项与调查活动；可继续调查或深度重测。

用户不需要手工告诉 Goose 某个测试产品是什么，系统应自行根据证据调查。人工提供的名称可以帮助定位，但不能替代泛化验收。

### 11.2 查看资产

点击模型、工具/MCP、规则、技能或网络资产卡片，在抽屉中查看名称、基本信息、路径和依据。原始 JSON 用于调试，应与人可读内容分开。

### 11.3 查看真实输入输出

在目标卡片中打开“Hook 实时数据”。优先看已采集的会话正文；需要定位时再展开原始记录。只看到 `model`、`message_id` 等元数据，而没有文字正文，不算已经采集用户输入。

有些测试消息包含唯一验收标记；它们证明的是对应测试会话。查看正常聊天时，应核对目标实例、会话、时间和文本，不要用测试会话替代当前用户会话。

### 11.4 查看自检

自检显示通过数量、待验证项和异常项。加载、输入正文或工具事件分别通过，不会让其他项目自动变绿。窗口不完整时，先扩大读取范围或核对生产端日志，区分展示截断与真正丢失。

## 12. API 参考与调用示例

以下列出当前代码中的主要接口，不是稳定的外部平台版本承诺。看板示例地址为 `http://127.0.0.1:8081`；独立服务示例为 `http://127.0.0.1:8099`。

### 12.1 看板读取接口

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/state` | 当前扫描、卡片、观测和能力快照 |
| GET | `/api/hook-data` | 原始与归一化事件、正文、覆盖、自检 |
| GET | `/api/hook-events` | Hook 数据别名 |
| GET | `/api/hook-data/download` | 下载当前筛选条件下的数据 |
| GET | `/api/investigation/activity?pid=12345` | 调查活动与工具过程 |
| GET | `/api/fingerprints` | 指纹与候选配方库 |
| GET | `/api/capability?pid=12345` | 能力阶段投影 |
| GET | `/api/native-trust` | 原生信任诊断报告 |
| GET | `/api/model-settings` | 模型配置摘要与验证状态 |
| GET | `/api/recipe-bundle/export?fingerprint_id=harness-01` | 按指纹编号导出配方包；可选 `note` |

Hook 数据常用参数：`pid`、`create_time`、`instance_id`、`since`、`until`、`limit`、`max_bytes`。建议同时传 PID 和创建时间，或传完整实例编号。

```bash
curl -sS 'http://127.0.0.1:8081/api/state'
curl -sS 'http://127.0.0.1:8081/api/hook-data?pid=12345&create_time=1780000000.123&limit=200&max_bytes=2097152'
```

返回结构概览，数组内容省略，不代表真实实例已通过：

```json
{
  "status": "ok",
  "filter": {"pid": 12345, "create_time": 1780000000.123},
  "bindings": [],
  "records": [],
  "normalized_records": [],
  "events": [],
  "conversation": [],
  "vocabulary": {},
  "coverage": {
    "io_acceptance": {},
    "integration_selfchecks": []
  }
}
```

`status=ok` 表示本次读取完成，不表示输入输出或控制已验收。

### 12.2 看板操作接口

| 方法 | 路径 | 请求或说明 |
|---|---|---|
| POST | `/api/scan` | 启动后台扫描 |
| POST | `/api/scan-interval` | `{"scan_interval":60}`；整数 1～86400 秒 |
| POST | `/api/model-settings` | `base_url`、`model`、`api_key`；异步验证，通常返回 202 |
| POST | `/api/reinvestigate?pid=12345` | 重新调查目标 |
| POST | `/api/reinvestigate/continue?pid=12345` | 依据同一实例的已保存证据续查 |
| POST | `/api/reinvestigate/cancel?pid=12345` | 请求取消运行中的调查 |
| POST | `/api/onboarding/execute?pid=12345` | 执行当前计划，仍检查部署授权 |
| POST | `/api/onboarding/verify?pid=12345` | 核实接入与观测 |
| POST | `/api/native-trust/refresh` | 更新原生信任诊断，不等于自动批准信任 |
| POST | `/api/recipe-bundle/import` | 提交 bundle 与目标构建/工作区信息 |

```bash
curl -sS -X POST 'http://127.0.0.1:8081/api/scan'
curl -sS -X POST 'http://127.0.0.1:8081/api/scan-interval' \
  -H 'Content-Type: application/json' -d '{"scan_interval":60}'
```

### 12.3 控制接口

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/hook-control/status` | 策略、待确认请求和控制事件 |
| POST | `/api/hook-control/policy` | 设置默认决定与规则 |
| POST | `/api/hook-control/decision` | 目标侧提交执行前决定请求 |
| POST | `/api/hook-control/resolve` | 对待确认请求返回 allow 或 deny |
| POST | `/api/hook-control/ack` | 目标侧报告决定应用回执 |

决策请求示例：

```json
{
  "pid": 12345,
  "create_time": 1780000000.123,
  "call_id": "tool-call-1",
  "tool": "write_file",
  "input": {"path": "isolated-check/marker.txt", "text": "check-marker"}
}
```

返回示例：

```json
{
  "request_id": "decision-request-1",
  "decision": "deny",
  "reason": "policy",
  "enforcement_verified": false
}
```

`enforcement_verified=false` 明确指出服务端返回决定还不能证明目标的执行效果。

建议目标侧使用已有客户端，从配置文件读取凭据，避免在日志或命令行中粘贴 Token：

```bash
python runtime/hook_control_client.py /absolute/path/hook-control-client.json decision < request.json
```

修改策略会影响匹配目标的后续操作，验收结束后应恢复原策略，不能把临时拒绝或确认规则遗留在日常环境中。

## 13. 独立 Hook 服务与平台对接

### 13.1 独立服务的职责

独立服务不扫描新进程、不启动 Goose、不学习配方；它读取已经登记的绑定与日志，提供正文和控制接口。停止发现界面后，它仍可服务这些已绑定目标。

需要保留的内容包括目标侧 Hook、Python 运行依赖、控制客户端及其配置、凭据、实例绑定、日志来源和策略状态。只有它们都可用，并且目标侧地址已指向独立服务，才能声称这条运行链路不依赖发现看板。

### 13.2 配置与启停

示例 `hook-runtime.json`，所有环境变量值使用字符串：

```json
{
  "ASG_RUN_DIR": "/absolute/path/to/shared-run-directory",
  "ASG_HOOK_HOST": "127.0.0.1",
  "ASG_HOOK_PORT": "8099",
  "ASG_HOOK_REMOTE": "0"
}
```

```bash
python hook_runtime.py start --config /absolute/path/hook-runtime.json
python hook_runtime.py status --config /absolute/path/hook-runtime.json
python hook_runtime.py stop --config /absolute/path/hook-runtime.json
```

启动命令返回进程已创建后，还需查询 `/health` 确认真正就绪。修改服务地址不会自动证明所有已安装 Hook 客户端都已改用新地址；需要核对 `hook-control-client.json` 及实际调用。

独立服务额外提供 `GET /health`、`GET /api/instances`、`GET /api/conversation`。Hook 数据与控制接口复用同一套实现。默认仅本机访问示例更便于初始验证；需要远程时再设置监听、远程开关和凭据。

### 13.3 AI Trust 与其他平台

`runtime/ai_trust.py` 包含本地字段映射、请求封装、待发送队列、重试和离线补发机制。代码中的 `/v1/instances`、`/v1/events`、`/v1/decisions` 等是当前连接器契约，不能当成已确认的 AI Trust 官方接口。

完成真实平台接管还需：双方确认认证与数据协议；验证事件送达和去重；核对策略返回；验证目标执行效果；停掉发现程序后继续运行；验证断网与恢复。仅填一个地址或本地模拟服务返回成功，不足以替代这些验收。

不要直接编辑 JSON 把状态改成“通过”，也不要只删除索引而误认为已经卸载目标侧 Hook。卸载要恢复目标配置并处理已安装文件；回滚前还需确认没有覆盖用户后续修改。

## 15. 验收标准与测试方法

### 15.1 自动自检 8 项

| 检查 | 通过条件 |
|---|---|
| Hook 加载 | 当前实例存在实际 `hook.loaded` 事件 |
| 用户正文 | 当前实例可提取非空用户正文 |
| 助手正文 | 当前实例可提取非空助手正文；完整性由下一项检查 |
| 完整回合计数与关联 | 至少一个回合通过正文、编号、序列、模型配对和结束计数检查，且没有来源问题 |
| 工具参数与结果 | 已通过检查的回合中有真实工具前后配对，不能以零次工具代替 |
| 放行与拒绝效果 | 当前实例及当前 Hook 字节绑定的独立效果证据 |
| 执行前等待决定 | 同一有效证明中包含 `decision_wait` 及放行、拒绝效果 |
| 采集来源与编号 | 当前窗口有数据且来源与标识检查无异常 |

8/8 表示该实例在已检查窗口与证据范围内通过自检，不是全部历史和未来流量均无丢失的保证。

### 15.2 完整回合的具体检查

- 事件编号非空且不重复。
- 回合内序号为连续正整数，没有缺口或重复。
- 所需事件存在实际内容，完整标记为真，且未截断。
- 每个模型请求编号恰好对应一次请求和一次响应。
- 每个工具调用编号恰好对应一次执行前和一次执行后事件。
- 同一实例、会话、回合与子 Agent 下恰好有一个结束检查点。
- 结束检查点包含六类输入输出事件的实际期望计数，并与采集记录一致。
- 若本轮没有工具，生产端明确声明工具计数为零；服务端不能自行猜测。

计数应来自生产端调用入口，不能由已经送达的日志反推，否则无法发现未送达事件。

### 15.3 推荐的真实目标验收批次

以下是验收方案，不是本文声明已全部完成的测试结果。

| 批次 | 具体操作 | 量化标准 |
|---|---|---|
| 正常聊天 | 同一正常实例完成 10 个回合，保存实际输入和可见输出 | 10/10 可关联；逐字对账零差异；不同实例不能拼成 10 回合 |
| 模型调用 | 对请求、完整响应、流式结束和重试记录核对 | 请求/响应匹配率 100%；中断必须标为不完整 |
| 工具记录 | 执行 10 次有独立结果可核对的可控工具任务 | 参数与结果 10/10 可关联，无重复计为新调用 |
| 放行/拒绝 | 各做 5 次唯一标记文件操作 | 放行 5/5 内容正确；拒绝 5/5 无副作用 |
| 等待决定 | 做 5 次延迟至少 2 秒的控制决定 | 5/5 在决定前无副作用；决定后符合结果 |
| 重启复用 | 连续 3 次退出再启动 | 3/3 新实例身份；不继承旧成功；新事件绑定正确 |
| 独立服务 | 连续运行 60 分钟，每 30 秒采样 | 121 个采样点均有结果；核对进程身份、服务可达和缺失记录 |
| 页面延迟 | 记录至少 30 个事件从发生到页面出现的时间 | 报告样本数、时钟方法、P50、P95、最大值和遗漏数；建议同机演示 P95≤5秒，需作为目标单独验收 |

## 16. 常见问题与排障

| 现象 | 优先检查 | 判断与处理 |
|---|---|---|
| 新 Agent 没出现 | 是否存活、扫描周期、权限、进程归属和候选阈值 | 留存进程证据，修复通用画像信号；避免仅加名字掩盖漏报 |
| 普通应用大量出现 | 是否只有弱信号、是否混淆工具服务与 Agent | 分析误报信号组合和角色证据 |
| 调查一直排队 | 并发数量、现有任务、失败冷却 | 查看调查活动，区分排队与实际运行 |
| Goose 不可用 | CLI 路径、模型设置、验证回复、服务容量 | 协议可直连时先尝试；回退所需条件缺失时明确报告 |
| 只生成候选未安装 | 安装开关、授权目录、文件计划与哈希 | 看安装结果，不靠候选文字判断 |
| 已安装但无事件 | 加载时机、原生信任、回调路径、祖先进程绑定 | 新会话/重启后核对真实回调；不重复覆盖正常配置 |
| 有事件但无正文 | 是否仅工具/加载、正文在哪个字段、是否只有元数据 | 同时检查原始记录与归一化结果 |
| Skills 数量不对 | 用户/项目/插件作用域、符号链接、枚举页与限制 | 记录已查路径和剩余范围；不要用前几项当全量 |
| 只有测试对话 | 实例、会话与标记 | 转到正常实例核对真实用户文本 |
| 返回 deny 仍执行 | 目标是否同步等待、原生返回语义、是否存在绕行工具 | 用独立副作用检测定位执行控制断点 |
| 自检来源异常 | 日志截断、未完成行、解析失败、缺少标识 | 扩大窗口或查原始日志，区分展示限制和实际丢失 |
| 独立服务启动但不可用 | `/health`、进程创建时间、端口冲突、运行日志 | 启动打印不等于就绪，必须请求服务验证 |
| 局域网页面开不了 | 监听地址、主机 IP、网络与防火墙 | 不要在另一台机器访问 `127.0.0.1` |
| 停掉看板后控制失效 | Hook 客户端是否仍指向 8081 | 配置到正确独立服务并验证实际决定链路 |

## 17. 开发导航与扩展方法

扩展时优先处理协议与行为结构，避免针对测试产品添加硬编码名称分支。

### 17.1 新增协议家族

1. 明确该协议提供的事件、传输、生命周期和权限语义。
2. 在协议检测模块增加结构匹配；加入“名称相似但结构不符”的负例。
3. 实现可复用接入器，保留配置和回滚事务。
4. 将事件映射到统一格式；未知信息保留为空并报告。
5. 验证传输真实接通，再验证内容覆盖，最后验证执行控制。
6. 在真实目标上测试重启、版本变化、失败与回退。

### 17.2 修改事件格式

同步检查生产端、`event_vocabulary`、`protocol_events`、`io_acceptance`、原始 API 和会话展示。增加流式中断、重复事件、跨会话串号、跨实例混用的负例，不只测试字段名存在。

### 17.3 修改安装或复用

保留原文件哈希前置条件、目录边界与事务备份。测试文件已被用户改动、已有绑定、目标退出、并发实例和回滚。历史人工修订应保留来源，不能重新标成 Goose 自主发现。

### 17.4 提交与交付

本次交付已整理协议与部署源码；具体执行结果见发布记录。私人运行资料、凭据和实例指纹不作为默认安装数据。不要直接把整个 `artifacts/` 或本机 `.env` 当成发布包上传。

## 18. 已知限制与后续工作

优先级从当前使用体验出发：

1. **扩大直接协议覆盖**：当前支持 JSON/JSONC/TOML 中唯一兼容命令式 Hook 和 agent_servers ACP 启动声明；没有现成条目和其他配置方言仍需调查。
2. **完善调度解耦**：直接协议尝试已经在 Goose 启动前，但仍位于自动调查调度入口；应进一步明确无 Goose 部署下的独立启用方式。
3. **补齐真实目标正文与模型通道**：命令式回调通常无法天然提供全部模型网络请求响应，需要其他已验证通道补齐。
4. **提高资产调查完整性**：技能、MCP 与规则需继续验证路径范围、分页和真实激活关系。
5. **完成正常实例验收**：真实聊天逐字对账、工具批次、控制等待与副作用、重启绑定不能用隔离模板测试代替。
6. **独立运行与迁移**：明确并验证运行依赖闭包、客户端地址、凭据和日志迁移；源码变化后旧耐久报告需重新核对。
7. **外部平台与跨机器**：完成真实 AI Trust 协议确认、跨机器路径/权限/构建兼容验收。
8. **工程发布**：整理确定版本；针对局域网管理接口补统一认证、权限与运行数据管理，再讨论生产化。

更细的协议实现说明见 [协议优先接入](stage1/PROTOCOL_FIRST.md)。历史验收与会议对应材料保留在 `docs/stage1/`，其结论必须结合报告日期、目标实例和 Hook 版本使用，不能覆盖当前实际自检结果。
